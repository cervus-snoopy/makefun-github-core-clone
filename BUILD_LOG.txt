against real git. FOUR BUGS FOUND AND FIXED in smoke:
(a) receive-pack: readPktLines ran over the whole body incl. the pack
    ("PACK" is not a pkt-line header) -> HTTP 400. Parse commands only
    up to the first flush; pack starts after it.
(b) ls-refs: git clone sends `ref-prefix HEAD` — HEAD line was only
    emitted with no prefixes. Emit HEAD when any prefix matches "HEAD".
(c) v2 fetch without `done`: real git expects an acknowledgments-ONLY
    response, then it POSTs again with `done`. Sending the packfile in
    the same response dies "expected response end packet". (Suite client
    always sends `done`, so this only affects real git.)
(d) depth fetch: tag roots were dropped from the send set (only commits
    + trees). A want naming a tag object must ship the tag itself.
Also: readPack re-walked + re-inflated the whole pack a second time to
resolve OFS bases -> single pass with recorded positions + recursive
OFS resolver (correct for chained deltas).

BUG (e) shallow-fetch have-closure (found 19 Nov, fixed in store.go):
planFetch excluded the FULL closure of haves from the send set. For a
deepen-2 fetch the client holds the tip + its tree but NOT the tip's
parents — yet the full closure contains the parent, so the parent was
excluded as "already held" and the server shipped an EMPTY pack (correct
shallow-info, zero objects). Fix: haveClosure() walks haves but never
follows the parents of commits named in the client's shallow list
(boundary commits). A full (depth 0) fetch on a shallow repo now also
unshallows the old boundary. Verified with the kit's own GitClient:
deepen delivers parent + tree, not the grandparent; boundary moves.
Also verified: fetch-shallow-depth1, fetch-shallow-new-tip,
fetch-incremental, fetch-nothing-new all pass via the kit's check code.
